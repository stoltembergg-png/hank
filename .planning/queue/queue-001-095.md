# Executable PR Queue — PR-001..PR-095

Status: planejamento derivado exclusivamente de `Hank/.planning/source/sdd-input.md`; nenhum card abaixo constitui implementação, execução ou evidência de comportamento.

## Contrato da fila

- Esta fila cobre M0 Foundation, M1 Core Domain, M2 Agent Domain, M3 Provider System e M4 Chat Runtime.
- Os IDs permanecem sequenciais de `PR-001` a `PR-095`. O source pack declara M3 como `PR-056–PR-077`, mas enumera apenas até `PR-076`; `PR-077` foi preenchida como uma decomposição indispensável de provider application/invocation service. **Renumeração proposta: nenhuma**; o slot omitido é preenchido e não há lacunas.
- Categorias válidas usadas: `FOUNDATION`, `DOMAIN`, `INFRA`, `BACKEND`, `FRONTEND`, `SECURITY`, `TESTING`, `DEVOPS`, `DOCUMENTATION`.
- “Arquivos/crates prováveis” são alvos de planejamento, não confirmação de existência. Cada dependência é uma dependência de contrato/resultado, não apenas de arquivo.
- Gates são fail-closed: falha, ausência, timeout, skip ou evidência de SHA incorreto mantém a próxima PR bloqueada.

## Gates de release da fatia

- **Gate M0 / Foundation:** workspace, contratos de CI, segurança de dependências, documentação e fixtures têm checks reproduzíveis; nenhuma integração de produto é alegada antes do gate.
- **Gate M1 / Core Domain:** schema/migrations, entidades, repositories e serviços de Project passam testes de isolamento e transação; UI só consome application services.
- **Gate M2 / Agent Domain:** Agent e suas políticas são persistíveis, validadas, isoladas por Project e expostas por serviços antes de qualquer tela.
- **Gate M3 / Provider System:** provider-core, normalização, streaming, adapters, credenciais, registry, OAuth, discovery, health e fallback têm contract tests; nenhum provider concreto vaza para o domínio.
- **Gate M4 / Chat Runtime:** Session/Message, storage, context builder, state machine, streaming, cancelamento/retry, serviço, command e UI completam um caminho de chat single-agent observável; qualquer integração parcial fica `NO_GO`.

## Gate de saída M4 / v0.2 planejado

O gate é uma condição de planejamento, não uma afirmação de que foi executado. Para desbloquear a próxima fatia, a implementação futura deverá demonstrar, no SHA atual e em fixtures controladas:

- migrations aplicadas antes de repositories e isolamento Project/Agent/Session verificado;
- provider-core, normalized request/response, streaming events e provider application service consumidos sem imports de adapters no Agent Runtime;
- credenciais somente por OS keychain/Stronghold ou backend aprovado, nunca plaintext em SQLite, `.env`, localStorage ou logs;
- contexto com hierarquia determinística, budget bounded e omissões explícitas;
- execution state machine com exactly-one terminal state, cancellation e retry bounded;
- caminho `chat command → Session service → provider stream → Message storage → Tauri events → chat UI` testado com MockProvider determinístico;
- security/contract tests para malformed, stale, duplicate, cross-project, wrong identity, capability mismatch, secret leakage, XSS e unauthorized IPC;
- artifacts/evidence com repo, SHA/tree, schema/revision, OS, fixture hash e resultado `NO_GO` em falha/skip/timeout.

Sem esse conjunto de evidências, o próximo milestone permanece bloqueado e nenhum texto de changelog, comentário de IA ou status visual é considerado implementação/executado.
